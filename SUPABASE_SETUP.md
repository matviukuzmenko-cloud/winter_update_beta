# Подключение Supabase

## Что уже подготовлено

- Регистрация и вход по нику и паролю через Supabase Auth.
- После входа ник отображается на главном экране; гостю доступно явное продолжение без аккаунта.
- Избранное, заметки, полив, сезонные наблюдения, история Flora и настройки хранятся в `public.user_data`.
- Для сохранённых растений сайт показывает внутрисайтовое напоминание о проверке полива, когда отмеченный интервал прошёл; это ориентир, не push-уведомление и не точный график полива.
- Новый раздел «Мой сад» добавляет AI-анализ фото, синхронизируемый дневник с приватными фотографиями и персональные интервалы ухода.
- В «Ритме ухода» можно добавить растение из коллекции вместе с подсказкой атласа, отмечать проверки почвы в ежедневном чек-листе и получать сезонные напоминания о влажности воздуха. Отметка проверки не считается поливом; прогресс хранится вместе с планом ухода и синхронизируется с аккаунтом.
- Фото для AI-анализа отправляется Worker/Gemini только для обработки и не сохраняется автоматически. Фото дневника загружается в приватный Supabase Storage bucket только после явного сохранения записи.
- Помощница Silva отвечает на языке сайта — русском, украинском или английском; история чата и черновики хранятся отдельно для каждого языка.
- Silva Community использует отдельные публичные таблицы с Row Level Security: публикации и ответы доступны для чтения всем, а писать, ставить отметки «Нравится», сохранять публикации, редактировать свой профиль и управлять своими записями могут только вошедшие пользователи. Аватары и фотографии публичны.
- Браузерные push-напоминания требуют входа, разрешения браузера, VAPID-ключей и Worker Cron. Интервалы — повод проверить почву, а не автоматическое предписание полить растение.
- Главная страница показывает анонимную оценку уникальных браузеров за вчера по UTC и активных за последние две минуты. В браузере хранится случайный ID; Worker передаёт в Supabase только его HMAC-хеш, IP-адреса не записываются, дневные записи удаляются через 35 дней.
- Изменения коллекции, отметок полива и сезонных наблюдений можно отменить кнопкой «Отменить» в уведомлении в течение нескольких секунд.
- Включены Row Level Security и политики, ограничивающие записи их владельцем.
- Прямые INSERT/UPDATE в `user_data` закрыты; запись возможна только через ограниченную RPC с проверкой авторизации, размера данных и версии строки.
- Облачные изменения записываются с проверкой версии: одновременная синхронизация объединяет независимые изменения вместо молчаливой перезаписи.
- Без настроенного проекта сайт продолжает работать с локальным хранилищем браузера.

Для входа по нику без email используется сгенерированный внутренний адрес в домене `.invalid`. Это не настоящий почтовый адрес: включите вход без подтверждения email. У такого аккаунта не будет восстановления пароля по email. Пользователь сам придумывает пароль на сайте; пароли не записываются в таблицу сайта.

## Настройка проекта

1. Создайте проект в Supabase и дождитесь завершения запуска.
2. В **Authentication → Providers → Email** разрешите вход по паролю и отключите **Confirm email**. Это необходимо, потому что аккаунт идентифицируется ником и у него нет настоящего email для подтверждения.
3. В **SQL Editor** выполните весь файл [`supabase/schema.sql`](./supabase/schema.sql).
4. Затем выполните [`supabase/migrations/20261030_concurrent_user_data_sync.sql`](./supabase/migrations/20261030_concurrent_user_data_sync.sql). Миграция безопасна для существующих данных: добавляет номер версии и атомарную RPC-функцию, не удаляя и не преобразуя записи аккаунтов.

5. Выполните [`supabase/migrations/20261031_garden_journal_and_push.sql`](./supabase/migrations/20261031_garden_journal_and_push.sql). Она создаёт таблицу подписок с RLS и приватный Storage bucket `flora-journal` с ограничением фото 2 МБ и доступом только к папке владельца.
6. Выполните [`supabase/migrations/20261104_public_visitor_stats.sql`](./supabase/migrations/20261104_public_visitor_stats.sql). Она создаёт защищённый от публичного чтения счётчик уникальных браузеров и RPC, доступную только роли `service_role`.

   Если Supabase уже настроен, не запускайте повторно базовую схему: примените все неприменённые миграции по порядку — 20261030, 20261031, 20261104, затем 20261106. Для Silva Community после основной миграции `20261106_silva_community.sql` примените `20261106_silva_community_features.sql`. Миграции не удаляют записи пользователей.
7. В **Project Settings → API** скопируйте Project URL и публичный `publishable` key (или legacy `anon` key) в [`supabase-config.js`](./supabase-config.js). Project URL должен выглядеть как `https://your-project.supabase.co` — без `/rest/v1/`. Не добавляйте `service_role` или `secret` key в сайт.
8. Настройте Worker:

   ```sh
   npm install
   npx wrangler login
   ```

   Укажите тот же Project URL в `SUPABASE_URL` файла [`wrangler.toml`](./wrangler.toml). В Cloudflare сохраните Supabase `service_role` key только как Worker secret:

   ```sh
   npx wrangler secret put SUPABASE_SERVICE_ROLE_KEY
   ```

   Для фото-диагностики также должен быть задан существующий Worker secret `GEMINI_API_KEY`; не помещайте ключ Gemini или Supabase в HTML.

9. Для push создайте отдельную VAPID-пару ключей в Node.js (приватный ключ не публикуйте):

   ```sh
   node --input-type=module -e 'import { webcrypto } from "node:crypto"; const pair=await webcrypto.subtle.generateKey({name:"ECDSA",namedCurve:"P-256"},true,["sign","verify"]); console.log("VAPID_PUBLIC_KEY="+Buffer.from(await webcrypto.subtle.exportKey("raw",pair.publicKey)).toString("base64url")); console.log("VAPID_PRIVATE_JWK="+JSON.stringify(await webcrypto.subtle.exportKey("jwk",pair.privateKey)));'
   ```

   Значение `VAPID_PRIVATE_JWK` вставьте в запрос `npx wrangler secret put VAPID_PRIVATE_JWK`. Значение `VAPID_PUBLIC_KEY` укажите в `wrangler.toml` и в `window.FLORA_VAPID_PUBLIC_KEY` в `index.html`; это публичная часть. Замените `VAPID_SUBJECT` в `wrangler.toml` на свой контакт `mailto:...`. Секреты `SUPABASE_SERVICE_ROLE_KEY` и `VAPID_PRIVATE_JWK` никогда не добавляйте в сайт или репозиторий.

   В `wrangler.toml` уже настроено ежедневное расписание Worker на 09:00 UTC. После настройки переменных и секретов разверните Worker:

   ```sh
   npx wrangler deploy
   ```

   `SITE_ORIGIN` в `wrangler.toml` должен указывать на `https://silvaquieta.com`. После смены адреса сайта Worker нужно развернуть заново.

   Worker также публикует `/robots.txt` с запретом для honeypot-маршрута `/api/internal/catalog-export`. Обращения к этому маршруту отвечают обычным `404`, ограничиваются отдельным `HONEYPOT_RATE_LIMITER` и дают в журнале приложения только событие с HTTP-методом — без записи IP, User-Agent или тела запроса. IP используется только как ключ Cloudflare rate limiter. Для включения защиты разверните Worker после настройки binding в `wrangler.toml`.
10. В Supabase откройте **Authentication → URL Configuration** и задайте `https://silvaquieta.com/` как **Site URL**. Добавьте `https://silvaquieta.com/**` и `https://community.silvaquieta.com/**` в **Redirect URLs**, если адреса ещё не указаны.

## Дополнительные эшелоны защиты

- **Доступ к аккаунтам и данным:** таблицы пользовательских данных, push-подписок, приватных фото и сообщества используют RLS. Не выдавайте `service_role` браузеру; для новых таблиц сначала включайте RLS и выдавайте только необходимые права. Публичные публикации, профили, комментарии и фото сообщества открыты по дизайну.
- **API:** Worker применяет IP rate limits к чату, диагностике, passkey, статистике и honeypot, ограничивает тела запросов и проверяет формат и размеры данных. Ответы API отправляют `nosniff`, `no-referrer` и `X-Frame-Options: DENY`.
- **WAF и бот-защита домена:** текущая публичная DNS-делегация использует `launch1.spaceship.net` и `launch2.spaceship.net`; Cloudflare WAF не управляет трафиком только потому, что приложение использует Cloudflare Worker. Настраивать WAF можно после перевода DNS/прокси к провайдеру с WAF. Перед сменой NS нужно перенести все существующие A/AAAA/CNAME, MX, TXT (включая почту и подтверждение домена), проверить записи и только затем включать проксирование. Не включайте блокировку по одному User-Agent: это легко обходится и может блокировать легитимных клиентов.
- **Публичный контент:** community feed отдаётся постранично через `community_feed` (30 записей в UI, максимум 50 в RPC; offset ограничен 10 000). Публичные данные принципиально можно копировать; лимиты снижают нагрузку, но не делают контент секретным.
- **Клиентский код:** JavaScript, который скачивает браузер, следует считать публичным. В клиенте должны оставаться только публичные ключи; секреты Gemini, Supabase `service_role` и приватные VAPID-ключи хранятся только в Worker secrets. Минификация/обфускация не заменяет авторизацию и RLS.

## Запуск пяти эшелонов и публикация обновления

Пункты 2, 3 и 5 можно публиковать из репозитория. Эшелон 1 требует активного Cloudflare proxy перед сайтами; honeypot из эшелона 4 также требует Worker route. Сейчас DNS домена делегирован на SpaceShip, поэтому пока не выполнен перенос NS и не включён proxy, WAF не защищает GitHub Pages, а Worker honeypot доступен только на адресе самого Worker.

### 1. Периметр домена: DNS, HTTPS и WAF

1. Создайте/откройте аккаунт Cloudflare и добавьте `silvaquieta.com`.
2. Создайте в Cloudflare DNS восемь записей из раздела «Перенос DNS в Cloudflare» в [`SUBDOMAINS_SETUP.md`](./SUBDOMAINS_SETUP.md). Сначала оставьте все записи **DNS only**.
3. До смены NS проверьте полный список в SpaceShip: в присланном снимке нет MX/TXT/CAA. Если используется почта или есть verification TXT, добавьте эти записи в Cloudflare тоже.
4. Когда Cloudflare подтвердит импорт, возьмите **назначенные именно вашему домену** nameservers из Cloudflare и замените NS в SpaceShip. Не удаляйте старую зону, пока новая делегация не Active и сайт/поддомены не проверены.
5. Проверьте `https://silvaquieta.com`, `www`, `ailab`, `community` и `os`. После успешной проверки включайте proxy сначала для одного hostname, перепроверяйте сертификат и GitHub Pages, затем переходите к следующему. Если HTTPS/GitHub Pages ломается — немедленно верните эту запись в DNS only и разберите origin TLS до повторной попытки.
6. Только после включения proxy включайте доступные вашему тарифу Managed WAF/Bot правила. Начните с Managed Rules и постепенного Challenge для подозрительной частоты/API; не блокируйте поисковых ботов или всех клиентов по одному User-Agent.

### 2. Защита аккаунтов и данных: Supabase

1. В Supabase проверьте список применённых migrations. Применяйте **только отсутствующие** миграции по порядку, указанному в начале этого файла; не повторяйте базовую схему поверх настроенного проекта без необходимости.
2. Убедитесь, что приватные таблицы и bucket `flora-journal` имеют RLS, а публичный `silva-community` содержит только контент, который пользователи явно публикуют для всех.
3. Проверьте **Authentication → URL Configuration**: Site URL и Redirect URLs должны соответствовать реальным HTTPS-доменам. Не расширяйте redirect allowlist на произвольные домены.
4. Не публикуйте `service_role` и не делайте приватные таблицы доступными роли `anon`. В Worker есть passkey API, но в этой рабочей копии нет SQL-миграции для таблиц `passkey_challenges` и `passkey_credentials`; не включайте passkey-вход в production до добавления и применения отдельной проверенной миграции и подключения UI.

### 3. API: секреты, лимиты и размер запросов

Из корня проекта:

```sh
npm install
npx wrangler login
npx wrangler secret put SUPABASE_SERVICE_ROLE_KEY
npx wrangler secret put GEMINI_API_KEY
npx wrangler secret put SERPER_API_KEY
npx wrangler secret put VAPID_PRIVATE_JWK
npx wrangler deploy
```

Для каждого `wrangler secret put` вводите только реальное значение соответствующего секрета; не сохраняйте его в HTML, JS, `wrangler.toml`, git или сообщениях. `SERPER_API_KEY` нужен для веб-поиска AI, `VAPID_PRIVATE_JWK` — для push; если функции не используются, их секреты можно не задавать. Проверьте, что Worker действительно привязан к уже объявленным `CHAT_RATE_LIMITER`, `DIAGNOSIS_RATE_LIMITER`, `VISITOR_RATE_LIMITER` и `HONEYPOT_RATE_LIMITER`. Ошибка настройки должна проявляться как `503`, а не как обход ограничения.

После deploy проверьте `/api/health`, затем безопасно проверьте, что превышение лимита возвращает `429`, слишком большое тело — `413`, а неверный Origin — `403`. Не отправляйте реальные пользовательские данные для этих проверок.

### 4. Honeypot и журналирование

`robots.txt` только сообщает совместимым роботам не ходить на `/api/internal/catalog-export`; это не механизм блокировки. После того как зона в Cloudflare станет Active и Worker будет авторизован для зоны, добавьте в `wrangler.toml`:

```toml
[[routes]]
pattern = "silvaquieta.com/api/internal/*"
zone_name = "silvaquieta.com"
```

Затем повторно выполните `npx wrangler deploy`. Не назначайте Worker на весь домен: маршрут должен покрывать только `/api/internal/*`, чтобы статика продолжала обслуживаться GitHub Pages. Проверьте, что путь отвечает `404`, а превышение отдельного лимита не приводит к обращению к Supabase. В прикладной журнал пишется только метод; IP используется Cloudflare как ключ rate limiter.

### 5. Клиент и публикация сайтов

Публичный фронтенд не может скрыть HTML/JS или сделать опубликованные community-посты непригодными для копирования. Не добавляйте блокировку DevTools, принудительные циклические переходы, fingerprinting или бесконечные вычисления: они не защищают данные и могут ломать сайт посетителям. Текущий `security-monitor.js` — безвредное production-only уведомление; не считайте его границей безопасности.

Опубликуйте соответствующие изменённые файлы в каждом отдельном GitHub Pages source/repository:

- основной сайт: `index.html`, `security-monitor.js`, `robots.txt`;
- AI Lab: `ailab/index.html` и `ailab/security-monitor.js`;
- Community: `community/index.html` и `community/security-monitor.js`;
- OS landing: `os-site/index.html` и `os-site/security-monitor.js`;
- Silva OS web/PWA: `silva-os/index.html`, `silva-os/security-monitor.js`; для репозитория standalone-публикации — также `silva-os-github-upload/index.html`, `silva-os-github-upload/security-monitor.js` и содержимое `silva-os-github-upload/app/`.

После публикации дождитесь завершения GitHub Pages deployment и проверьте HTTPS, основные сценарии приложений, AI API, вход/выход и чтение только собственных приватных данных. Локально `security-monitor.js` ничего не делает на `localhost`; `npm run tauri dev` не запускает production-проверку. Нативное приложение Silva OS публикуется отдельной Tauri release-сборкой, а не GitHub Pages.

## Публикация сайта на GitHub Pages

1. В настройках репозитория, где размещён сайт, откройте **Settings → Pages** и проверьте, что GitHub Pages публикует ветку и папку с `index.html`.
2. В поле **Custom domain** укажите `silvaquieta.com` и нажмите **Save**. Корневой файл `CNAME` уже содержит это имя.
3. В панели DNS регистратора направьте корневой домен на GitHub Pages: добавьте A-записи `185.199.108.153`, `185.199.109.153`, `185.199.110.153` и `185.199.111.153`. Если хотите также обслуживать `www.silvaquieta.com`, добавьте для `www` CNAME на `matviukuzmenko-cloud.github.io`. Удалите конфликтующие записи для настроенных имён.
4. Дождитесь обновления DNS, затем в **Settings → Pages** дождитесь включения HTTPS и отметьте **Enforce HTTPS**.
5. После публикации разверните Worker командой `npx wrangler deploy` и обновите **Authentication → URL Configuration** в Supabase, как описано выше. Корневой адрес сайта — `https://silvaquieta.com/`.

Публикацию двух мини-сайтов, DNS и настройку сообщества см. в [`SUBDOMAINS_SETUP.md`](./SUBDOMAINS_SETUP.md).

Фотографии iNaturalist оптимизируются через публичный кэш-прокси wsrv.nl: запрос передаёт этому сервису URL открытой фотографии, а он отдаёт WebP подходящего размера и качества. Если прокси недоступен, сайт автоматически загружает оригинальный вариант iNaturalist напрямую. Другие источники изображений продолжают загружаться напрямую.

Имена пользователей приводятся к нижнему регистру для входа. Ник должен содержать 3–24 буквы, цифры, `_`, `-` или `.`; пароль — не короче 8 символов. Изменять политики RLS или делать таблицу доступной для `anon` не нужно.

После входа локальные данные объединяются с облачными. При совпадении заметок используется локальная запись, для дат полива — более поздняя дата, для сезонных наблюдений и избранного — объединение. Настройки и история чата также синхронизируются между устройствами.

При параллельном обновлении аккаунта клиент сравнивает версию перед сохранением. Если данные успели измениться на другом устройстве, приложение повторно читает актуальную версию и объединяет независимые изменения; коллекция и сезонные отметки объединяются по добавлениям/удалениям, заметки — по растению, даты полива — по более поздней дате. Если миграция не применена, синхронизация покажет ошибку и попросит выполнить SQL-файл миграции; локальные данные при этом остаются в браузере.
